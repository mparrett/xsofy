## Key Decisions

### Architecture / methodology choices that shaped the session

- **Telemetry before profiling.** Per-turn ms via `bridge/emit-perf` + `dbg/log` landed first. Without it we'd have had no signal for which subsystem to drill into, and pprof's flat distribution would have been mute. The two infrastructure layers compounded.

- **Subsystem attribution before Go pprof.** The plan deliberately put per-phase ms inside `update-world` ahead of any Go profiling. Result: when pprof later showed `Frame.Run` at 22% and GC at 38%, we already knew the cost was concentrated in `run-until-player-turn`, which turned a flat profile into actionable guidance. Reverse order would have led to "VM is the bottleneck" with nowhere to go.

- **Headless replay over scenario benches.** Considered building `bench/scenarios.lg` with `step-fire(N)` / `ai-tick(N)` sweeps. Rejected for this session — the keystream-driven `bench/replay.lg` was sufficient to drive the audit, and adds zero invasiveness. Scenario benches would have answered "how does subsystem X scale with input size?" — useful, but a follow-up question.

- **Patch templates, not one-offs.** Both patches in `64b8833` apply patterns that recur in the codebase. Wrote them so the rewrite is easy to spot-check and easy to replicate. The handoff explicitly preserves the second pass as a separate session so the comparison numbers don't drift across compounding changes.

- **Skipped <code>reduce-kv</code>.** Let-go's stdlib doesn't have `reduce-kv`. The single-pass rewrite uses `reduce` over `(vals (:entities world))` instead — slightly less efficient (still allocates a `vals` seq, but only one) but stable and present in the runtime. If `reduce-kv` lands upstream (or in our fork) it'd be a one-line follow-up swap.

### Tests have a known flaky case

`tests/world.lg`'s `(= hp0 hp1)` assertion fails roughly 1 in 5 runs (RNG-seed dependent — when the player spawns next to fire or in a melee-able tile, hp changes after one turn). Documented in `CLAUDE.md`. Re-run `lg tests/run.lg` 2–3 times if it fails after a change; if it consistently fails, the change is probably the cause.

### Bench numbers swing significantly run-to-run

A "cold" `bench/replay.lg` run can show 2-3× higher per-turn numbers than a "warm" run on the same code. The variance is from Go GC pacing, page cache warmth, and (much smaller) the non-deterministic RNG seed driving world generation. Don't trust a single run; use 5 trials and look at medians or distributions. The pprof samples are over a single run, so a single anomalously slow run can skew the profile — re-run to confirm the bigger picture before drawing structural conclusions.

### `bench/perf-detail.lg` has a methodological limit

The current `bench/perf-detail.lg` (Methodology B in the audit doc) measures subsystem cost in isolation by calling each function K times on the *same* warm-world snapshot. For functions whose work depends on world evolution (entity ticks accumulating, fire spreading) this gives misleadingly low numbers — calls 2+ short-circuit because the world hasn't advanced. The header comment notes this explicitly. For trustworthy sub-phase attribution, use Methodology A (the `*perf-detail*` flag + in-update-world markers, currently un-wired).

### The pprof `-cpuprofile` file relies on clean main exit

The flag wires `pprof.StopCPUProfile` via `defer`. If `lg` exits via `os.Exit(1)` on an error, the deferred stop won't fire and the file may be incomplete. The bench script runs to completion under normal conditions, so this hasn't been an issue. If you're profiling something that errors out, expect a corrupted profile and fix the error first.
