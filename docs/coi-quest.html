The bundle rendered the title screen, then asked the player for a key and threw. The user reported it on a phone. The probe never reproduced it. The fix was nine words of JSON. Everything between those facts is this document.

Act I ᛟ

The read-key curse — why a working test rig can hide a real bug

let-go compiles (term/read-key) to a synchronous wait on a SharedArrayBuffer via Atomics.wait — the only way to do blocking input from JavaScript without ceding the main thread. SharedArrayBuffer is only exposed inside a cross-origin-isolated context.

The Playwright probe ran against http://localhost:8000. Browsers exempt localhost from the secure-context requirement, so isolation was implicit — input worked, the title advanced, kobolds were fought. We declared victory and moved on.

The user was tapping from a phone on the LAN, where no such exemption applies. The bundle's bootstrap detected the missing isolation, fell into a degraded "main-thread mode" that can render but cannot read input, and (term/read-key) threw on the first tap.

#error {:message "read-key: terminal input not available (no SharedArrayBuffer)", :data {:trace ("new-game" "show-title-screen" "read-key")}}
Act II ᛏ

The cert maze — mkcert, untrusted trust, a tunnel detour

To get a non-localhost origin into the cross-origin-isolated club we needed HTTPS. mkcert was already installed from a previous project — the root CA file sat in ~/Library/Application Support/mkcert/ dating back to 2022. We generated a fresh cert covering 127.0.0.1 and the LAN IP, swapped in npx serve --ssl-cert ... --ssl-key ..., and confidently visited the LAN URL.

Chrome: "Not Secure." Phone: profile installed but trust setting never propagated. The mkcert root was in the keychain but not in the trust store — mkcert -install had been run, but without sudo, which silently fails to write the system-wide trust entry.

We tried a Cloudflare tunnel to sidestep the cert work. It served the bundle over a real cert from a public CA, which fixed cert trust everywhere instantly. The user's phone still hit the same FATAL on the first tap. Transport was never the problem.

Act III ᛇ

The reload loop & the header mismatch — a 6.3 MB bundle re-instantiating itself to death

The bundle ships a coi-serviceworker.js — a one-page service worker that re-fetches every response and stamps it with cross-origin-isolation headers. On registration, the bootstrap reloads the page so the SW can intercept this time around.

Two layered defects:

One: register(...).then(() => location.reload()) fires on the SW being registered, not on it becoming the page's controller. On Safari the second load arrives before the SW is in charge, so isolation is still off, the reload condition fires again, infinite loop. On mobile this re-instantiates 6.3 MB of WASM per cycle. The user thought their phone was crashing. The user was right.

if (crossOriginIsolated) { sessionStorage.removeItem('coi_reload_attempted'); } else if (!sessionStorage.getItem('coi_reload_attempted')) { sessionStorage.setItem('coi_reload_attempted', '1'); // one-shot guard navigator.serviceWorker.register('coi-serviceworker.js').then(() => { if (navigator.serviceWorker.controller) location.reload(); else navigator.serviceWorker.addEventListener('controllerchange', () => location.reload(), {once: true}); }); }

Two: the SW set Cross-Origin-Embedder-Policy: credentialless. That's a Chrome-96+ value Safari has never implemented. With an unrecognized COEP value, Safari treats COEP as unset and isolation never activates. The SW could install, control the page, and stamp headers all day — Safari would not care. Patched to require-corp plus a Cross-Origin-Resource-Policy: cross-origin on every response so the cross-origin xterm.js scripts from jsdelivr would still satisfy the stricter embedder policy.

jsdelivr already sends cross-origin-resource-policy: cross-origin on its CDN responses. Confirmed via curl -I before committing to require-corp.

Act IV ᚱ

The principled path — what the service worker was working around

The user, mid-saga, observed the obvious thing. The service-worker shim exists for hosts where you can't set response headers — GitHub Pages, static blobs. We were running npx serve. We could just set the headers ourselves.

{ "headers": [{ "source": "**/*", "headers": [ { "key": "Cross-Origin-Opener-Policy", "value": "same-origin" }, { "key": "Cross-Origin-Embedder-Policy", "value": "require-corp" }, { "key": "Cross-Origin-Resource-Policy", "value": "cross-origin" } ] }] }

One serve.json later, the COI headers arrive on the first byte of the first response. Cross-origin isolation is live before any JavaScript runs. The bundle's !crossOriginIsolated branch never executes. The SW is never registered. The Safari mismatch becomes moot. The reload loop dies because there is nothing to reload for.

Playwright probe of the LAN URL from a fresh client: { coi: true, sab: true, navigations: 1 }. Title screen renders. First tap advances the game.

Act V ᛗ

The stale worker — old ghosts, new haunt

The fix shipped. The user's phone still bailed. A fresh Chromium via Playwright worked perfectly on the same URL.

Mobile Safari had cached the original broken service worker from our first attempt. It was still controlling every visit, dutifully replacing the server's good require-corp header with its old credentialless value, breaking Safari's isolation check anew. Even the patched bundle couldn't reach a client whose SW was a ghost from two hours prior.

A Private tab — fresh storage, no SW history — loaded the patched bundle into the patched server, met the patched cert (which by then we'd actually trusted), and ran. The title rolled. The user tapped. The dungeon descended.

What we learned

Five hours to one configuration file. The pattern is universal: when a working test rig contradicts a real-world bug, the test rig is cheating somewhere. localhost is exempt from a lot of rules that production isn't.

  1. Cross-origin isolation requires server-side COOP/COEP headers. The service-worker shim is a fallback for when you don't control the server. If you do, just set the headers.
  2. credentialless COEP is Chrome-only. Use require-corp + cross-origin CORP for portability.
  3. mkcert -install needs sudo on macOS to write the system trust store. Without sudo it succeeds silently and trusts nothing. Verify with security verify-cert.
  4. Auto-reloading on SW registration creates loops. Wait for controllerchange or fall back through a sessionStorage guard.
  5. Old service workers haunt clients indefinitely. After any SW change, validate in a Private window or after clearing site data — your normal tab is lying to you.
