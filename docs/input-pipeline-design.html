We were chasing a phone perf regression and surfaced the missing fourth number — input-pipeline lag, the time between a key entering the JavaScript side and the Go side finally returning it. Reading the gauge mid-game with a finger held into a wall, the gauge sat at 50ms while the lag read 351ms. The lag wasn't a transmission cost. It was depth.

Act I ⊟

The shape of the problem — what the gauge actually told us

A player holds a direction into a wall. The OS auto-repeat fires at ~30Hz. The engine processes each bumped-wall turn at ~50ms — about 20Hz. Producer outpaces consumer. The ring buffer, doing exactly what a buffer should, holds the excess.

The input-lag metric measures wall-clock from _lgKey writing a byte to term/read-key returning that byte. With a buffer at depth seven and an engine taking 50ms per turn, that's 50 × 7 = 350ms. Matches the capture exactly.

Seq of Concern · d 1 · hp 30/30 · t 53 u 32ms r 18ms i 351ms ← lag is 7× engine cost log: Blocked. (x116) ← same no-op turn, 116 reps

The lag a player perceives isn't the SAB notify-wait round-trip (microseconds). It's the geometry: queue_depth × engine_ms. Releasing the wall doesn't help — your new key joins the back of the queue.

Act II ≡

How the buffer is wired — current state, fully

The SAB is 256 bytes, mirrored constants in let-go/wasm.go (producer) and let-go/pkg/rt/term_wasm.go (consumer). Eight slots, 16 bytes per key payload, plus side channels for terminal dimensions and per-slot inject timestamps (the latter added for the i metric itself).

function sendKey(data) { const w = Atomics.load(keyInt32, WRITE_IDX); const r = Atomics.load(keyInt32, READ_IDX); if (w - r >= CAPACITY) return false; // full → silent drop // ... write slot, advance writeIdx, notify ... }

Two callers: term.onData (xterm.js, feeding real OS keystrokes including auto-repeat) and _lgKey (touch buttons, Playwright). Both ignore the return value. The only drop policy is "full → silent drop." Up to seven keys behind you, every one is accepted and dutifully queued.

The consumer blocks on Atomics.wait until the buffer is non-empty, reads one slot, advances readIdx by one. No knowledge of queue depth. No coalescing. No special handling. It is the simplest possible consumer.

When the queue fills, sendKey returns false; the OS keeps generating keys at its repeat rate; everything beyond the eighth queued key vanishes. From the OS's perspective, all its events were delivered into the page successfully. There is no backpressure anywhere.

Act III ▤

Where intelligence can live — five places to put a brain

Each location has a different reach and a different cost. The question is not which one is correct — they all "work" in the sense of stopping the buffer from filling — but which combination has the cleanest semantics and the most appropriate cost.

Where Mechanism Cost per write Catches
JS producer, O(1) Inspect slot (w-1) % 8. If same bytes as incoming, drop. 1 load + memcmp OS auto-repeat (always sends adjacent dupes)

Act IV ◊

The sixth place we considered — a Go-side in-memory buffer

A poller goroutine drains the SAB into a Go-memory queue; read-key reads from that queue instead of from SAB directly. Two would-be benefits:

  • Policies that need whole-queue inspection. Go memory supports maps, sets, priority queues — easier than atomics ops on SAB slots. You could express "drop everything before the most recent y/n confirm."
  • Timing decoupling. In multi-threaded Go, a poller drains SAB even while the engine is busy. The SAB stays shallow → producer rarely sees overflow.

The decoupling is illusory on WASM. Go in WebAssembly is single-threaded; a separate goroutine still time-shares with the main game loop. The poller only runs when the game yields. You haven't decoupled anything timing-wise — you've just moved the buffer from SAB-land to Go-land. The SAB is already the buffer.

On native (real terminal) there is no SAB at all. read-key is a blocking stdin read with kernel-level buffering. A Go-side queue there would be a different abstraction for a different problem; the WASM concerns don't transfer.

Set aside. Reconsider only if a future policy genuinely requires whole-queue inspection (priority routing, multi-byte sequence detection, etc.). For the held-wall problem we have today, consumer-side logic directly inside read-key is sufficient.

Act V ∺

How big should the queue be — the cap as a tunable knob

The queue exists for one reason: to absorb legitimate bursts — inputs that arrive faster than the engine processes but represent distinct user intents. Multi-tap diagonals, programmatic replay, future chord sequences. OS auto-repeat is a fake burst the buffer dutifully holds; the deeper the queue, the longer the tail when this happens.

Cap Held-wall tail latency Legit-burst absorption
8 (current)up to 400ms8 keys — overkill
4up to 200ms2–3 tap chords
2up to 100msbarely — 2-tap diagonal OK, more drops
1~50ms (one engine cycle)none — latest-wins

Combined with any consumer coalescing, the legit-burst column still bounds at queue size. But the held-wall column collapses to 0–1 regardless of cap. So if coalescing is in place, queue size mostly matters for non-duplicate bursts.

Why not just queue=1 and skip coalescing? Because then the producer rapidly hits "full" and drops keys silently. The player feels skippy holding — some auto-repeats land, others vanish. Coalescing produces the same net effect (one move per held burst) without the silent-drop semantics. Cleaner abstraction.

Act VI ✦

The proposed layering — recommendation, stage by stage

Stage in order; observe before adding the next. Each layer is independently useful and independently revertable.

  1. Consumer-side lazy coalesce in read-key. Greedily collapse adjacent identical keys before returning. Cheap, isolated to one Go function. Eliminates the held-wall bug. If we only have appetite for one tier, this is the one. It solves the immediate problem with the cleanest semantics.
  2. Queue cap → 4. Halves the worst-case burst tail even if coalesce somehow misses. Still absorbs typical legit bursts. One-line change to the mirrored CAPACITY / keyCapacity constants. Belt-and-suspenders against pathological inputs the coalescer doesn't see.
  3. JS producer O(1) dedupe — check just (w-1) % 8 for matching bytes. Catches OS auto-repeat before it ever enters the buffer. Very cheap. With this on top, even queue=4 stays at depth ≤1 during held-key. Tail latency stays under ~100ms even adversarially.

All three together: held-wall barely touches the buffer; legitimate bursts get through; the player never feels skipped or stuck. The pipeline becomes invisible.

Act VII ⌖

Failure modes worth watching — what could go wrong after we ship

  • Engine-rate-limited burst. Player taps the same direction five times deliberately at 200ms apart. Each tap fits in its own engine turn; coalescer doesn't merge non-adjacent keys; all five get through. ✓
  • Coalescing across distinct intents. What if "l l l" reaches the buffer because the OS sent rapid repeats, but the player meant three distinct moves? In practice human deliberate tap rate (5–10Hz) is slower than engine processing rate (~20Hz). Only auto-repeat queues; auto-repeat is the case where coalescing is correct.
  • Producer dedupe vs valid same-key sequences. Entering inventory, then immediately re-pressing the same direction. The dedupe window is just "what's currently in the buffer" — once the engine consumes the inventory key, the next direction key is fresh.
  • Smart-drain meeting auto-actions. If autoexplore is running and the user pre-queues a stop key, the engine should still drain held-direction keys from before autoexplore started. Not a concern for consumer coalesce; would matter only if we add Tier-V (engine-aware drain).

Open questions

Things we'll only know after the first tier lands and we look at the gauge again:

  1. Should coalescing apply to all keys, or only to known "movement" keys? Generic adjacency is simpler; movement-only would forbid any chance of merging deliberate sequences but adds a key-classification dependency.
  2. Is the i metric sufficient for diagnostics, or do we also want :queue-depth exposed in the perf payload? Cheap to add — one extra atomics load per read.
  3. After consumer coalesce ships, does i drop to single digits? If yes, the input pipeline is solved. If not, we have a different bottleneck to chase — and now we'll know it isn't the queue.
  4. Is the held-wall behavior the only auto-repeat trap, or are there other no-op-loop scenarios (failed equip, no arrows for bow, locked door without key) that produce the same shape? Worth a sweep.
