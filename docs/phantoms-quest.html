Yesterday's handoff named a parting threat: "the FitAddon doesn't refit cols on resize — verified by probe." Today began with that as the next thread to pull. The probe was wrong. The thread led elsewhere. What unspooled, before the day was out, was a small carnival of phone-shaped indignities — wrong viewports, ghost service workers, hand cramps from tap-tap-tapping — and at the end, a lantern to see by.

Act I ⚯

The phantom cols — a misread DOM attribute, a screenshot, a confident handoff

The handoff said FitAddon was failing to recompute columns on a dynamic resize: 1280px viewport → 375px viewport, rows shrank correctly, cols stayed at 150. A real bug; worth a ResizeObserver in the let-go fork.

Four probes later — direct term.cols, fitAddon.proposeDimensions(), buffer inspection through xterm's API, and an explored-map screenshot — the finding was that cols updates fine. 150 → 42 on the dot. The earlier probe had read .xterm-screen[aria-rowcount] and labelled it cols; that attribute is null on current xterm, and the symptom screenshot showed a map blob on the right side of the viewport — actually correct camera behaviour for a spawn at world column 71 of 79, with only the spawn FOV revealed.

term.cols 150 → 42 # corrected on resize term.rows 46 → 27 # corrected on resize proposed {cols:42, rows:27} # FitAddon agrees aria-rowcount null # not a thing on .xterm-screen

So: no fix. The right artifact was a written one — an ADR in docs/project_notes/decisions.md explaining the misdiagnosis so a future session wouldn't chase the same ghost. Cost: an hour. Benefit: not spending the next session adding a ResizeObserver to working code.

Phantom recorded. Real bugs awaited.

Act II ⌖

The truncated hint — and the first checked-in e2e smoke

The keybind hint at the bottom of the game (yuhjklbn:move .:wait eUda:item …) is 67 chars. On a 27-col portrait viewport it truncated to yuhjklbn:move .:wait eUd — useless. The HTML host bar already shows the action buttons, so the hint had nothing to add on phone.

One line in xsofy/ui.lg: gate show-status? on (and (>= gh 2) (>= gw 67)). When the row drops, the layout's rect-split-v gives that row back to the map. Trivial diff, real gain.

The more durable artifact was tests/e2e/shell_smoke.py, a Playwright probe promoted from a one-off in /tmp: 18 assertions covering DOM mount, event bus, _lgKey input path, portrait collapse (this hint-drop included), resize wake, and font cycle persistence. Boots once per scenario, runs in ~30s, exits 1 on failure. The same harness would carry every subsequent change today.

A subtlety we'd later need: the xterm accessibility tree includes invisible buffer cells past term.cols. A naive textContent match against .xterm-rows > div will happily find a "deleted" landscape hint sitting in zombie cells at column 67+. The fix is to read xterm's buffer through _lgTerm.buffer.active.getLine(y).translateToString(true).slice(0, t.cols) — which meant exposing _lgTerm from the let-go template as a documented diagnostic affordance.

Act III ◎

The vanishing glyph — one missing meta tag, two-and-a-half-times zoom

A screenshot arrived from an iPhone 13. The terminal worked, but all the characters were tiny. The HTML host bar at the bottom rendered at expected size; only the terminal area was undersized.

The reveal: the bar's font-cycle chip showed A14, but the layout was clearly using more than 80 columns (the sidebar was visible — its threshold). On a 390-CSS-px iPhone with fontSize 14, 80 cols would need a cell width of 390/80 = 4.875px. Impossible for fontSize 14. The conclusion forced itself: 100vw wasn't actually 390px.

Mobile Safari defaults its layout viewport to 980 CSS px when there's no <meta name="viewport"> tag. The terminal was rendering at desktop size — then being scaled down by Safari to fit the device — at roughly 39% of intended size. Every "collapse on narrow" branch in ui/layout was inert because the page never thought it was narrow.

<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">

One tag in the let-go fork's WASM template. With it, 100vw resolved to the real device width, fontSize 22 (portrait default) gave ~30 cols, the sidebar and hint dropped, and the map filled the viewport at full pixel density.

Act IV ⌬

The service worker maze — a loop, a guard, a header, a phone freeze

On the rebuilt bundle, the phone went into an infinite reload loop. Familiar territory: cross-origin isolation, the coi-serviceworker.js shim that yesterday's quest already half-defeated by sending COI headers from the dev server. But the SW was still living in Safari's storage, intercepting every fetch, rewriting our Cross-Origin-Embedder-Policy: require-corp into credentialless — a header Safari refuses to honour — and triggering the bundle's reload-on-register-completion path, which had no guard.

Three layered fixes, all in let-go/wasm.go:

1. A sessionStorage guard around the SW registration. If isolation never activates, we reload at most once per tab, then accept the degraded state instead of churning CPU forever.

2. Auto-unregister any leftover SW when the document is isolated. If the server headers worked, the SW is dead code — get it off the phone so future visits stay clean.

3. Fix the SW itself: stop overriding server-set COOP/COEP, and when the SW does need to inject headers (GitHub Pages, etc.), use require-corp (broadly compatible) instead of credentialless (Chrome-only). The combination undoes the trap that put us in the loop in the first place.

The user, mid-recovery, reported: "It worked and I don't really know why — I couldn't find a way to clear cookies because my phone froze." A phone freeze is also a way of clearing service workers. We accepted the win.

Act V ◇

The held direction — hold-to-repeat with a toggle, scoped to movement

With the phone playable, the next friction surfaced: tap-tap-tapping to cross a corridor. Roguelikes solve this with shift+direction run-keys, but a thumb on glass doesn't get modifier keys. Hold-to-repeat on the D-pad was the natural answer.

The implementation is small (~50 lines in dev/shell.html), but the decisions were the interesting part:

Scope. Only the .pad set (8 arrows + WAIT) repeats. Action buttons — GET, INV, FIRE, DESCEND, RUNES, MENU — deliberately don't. Holding FIRE re-fires the spell; holding INV opens-closes-opens the menu. Both are footguns.

Cadence. 200ms initial delay, 100ms interval (10 Hz). Picked to roughly match the engine's sustainable rate on a held wait — going faster just backs up the SAB busy-wait. See Act VI for why we know that number.

Surface. A small ↻on chip in the info row, next to the A22 font cycle. Tap to toggle; state persists to localStorage under xsofy/auto-repeat.

The cancel-on-release path is more careful than it looks: pointers can leave a button without firing pointerup on it (finger slides off, browser steals the event). The handler listens for pointerleave and pointercancel on each button, AND pointerup on the window itself as a final safety net. Without that, a drag-off-then-release left the timer ticking forever.

Result: hold any direction, walk smoothly. The e2e suite gained four assertions (multi-fire on hold, single-fire when toggled off, state persisted) so the behaviour stays put.

Act VI ⊹

The telemetry lantern — what is the engine actually doing all turn?

The hold-to-repeat probe surfaced an oddity: 1.0s of hold produced only 3 turns, not the 7 we'd expect from a 200/100ms cadence. Was it the engine, the JS timer, xterm, the SAB busy-wait, the bridge? The honest answer was: we'd been guessing.

A small instrumentation pass, both at the let-go and HTML layers:

Game side. Two System/currentTimeMillis markers around world/update-world and around the subsequent render call (full or dirty). Per-turn data goes out two channels: bridge/emit-perf (a JS event for the browser) and dbg/log (a line in debug.log for native). Native callers see the same numbers without involving the bridge; WASM callers can wire a listener with a single line.

Sample side. A checked-in tests/e2e/perf_sample.py, distinct from the regression smoke (it asserts nothing). Three workloads: discrete WAIT taps, held WAIT, autoexplore. Boots a fresh page per workload so prior world state doesn't confound the next sample.

scenario update render total rate discrete '.' taps 53ms 27ms 81ms ~10 Hz held WAIT (2s) 196ms 30ms 226ms ~4 Hz autoexplore (4s) 310ms 150ms 461ms ~2 Hz untracked overhead ~25 ms/turn (xterm paint + bridge + SAB)

Three discoveries fall out of this:

Same key, different cost. A discrete . press costs ~53ms in update-world; the same key held for 2s averages ~196ms. The action is identical — the difference is that "held WAIT" lets the world drift further from idle. Enemies wander into FOV, fire spreads, AI activity scales.

Render is mostly cheap. Dirty-rect repaints stay under 30ms in nearly every steady-state scenario. Autoexplore's 150ms render average is camera-shift triggered full repaints, not the per-cell incremental.

Input is not the bottleneck. The 10 Hz auto-repeat cadence is already faster than the engine can sustain when the world is active. Bumping to 12 Hz would just back up the SAB. The optimization targets are inside update-world: AI tick cost as activity scales, the every-turn fire/water/light passes, and (more speculatively) the full-vs-dirty render decision during a camera-tracking sequence.

Numbers, not guesses. Anywhere we want to take the next swing, we'll do it with the lantern.

What we learned

The day started with a phantom and ended with a dataset. In between, each "small UX nit" we touched turned into a structural fix — usually in the let-go fork, often a half-line of HTML, almost always at a seam between two layers (xterm and the document, the document and the SW, the WASM worker and the JS bridge).

  1. Verify before fixing — even your own handoff. Yesterday's session was confident enough about FitAddon to write it into Next Steps. A direct measurement said otherwise in 20 minutes. An hour of skepticism saved a half-day of fictional repair.
  2. The xterm accessibility tree lies about visibility. Buffer cells past term.cols stay populated; textContent includes them. Slice to t.cols via the buffer API, or your probes will pass on broken pages and fail on working ones.
  3. Mobile Safari assumes 980px until you tell it otherwise. Every responsive-design "this looks great on phone" rule is silently inert on iOS without a viewport meta tag. The render is correct; the scale is wrong; the symptom is "tiny chars."
  4. A service worker that fixes one device can poison another. Once registered, it controls every future fetch — even fetches that would have been fine via direct server headers. Belt-AND-suspenders means making each layer aware of the other: the SW shouldn't override what's already correct; the document should sweep up SWs it no longer needs.
  5. Telemetry is cheap; measurement debt is not. The instrumentation that produced Act VI's table was two System/currentTimeMillis calls and a one-line bridge emit. The two days of "is it the engine? is it xterm? is it the bridge?" before that were the actual cost.
