We keep talking about "WASM" as though it's a faster JVM or a different JavaScript. It's neither. WebAssembly is a sandboxed virtual ISA — an abstract CPU. It has integers and a single flat array of bytes and almost nothing else. Everything higher-level — objects, garbage collection, threads, file I/O — gets implemented on top by whichever language compiled to it. When you ship Go to WASM, the binary contains both your code and the entire Go runtime, recompiled to that abstract CPU.

Act I ⌹

What WASM actually is — a stack VM with no opinions

WebAssembly is a binary instruction format for a stack-based virtual machine, standardized as a W3C recommendation in 2017. Think of it as a portable ISA — like x86 or ARM — but designed to be safely runnable in untrusted environments. Originally browsers; now anywhere via WASI runtimes (Wasmtime, Wasmer, etc.).

The headline properties:

  • Stack-based execution. Operands pushed and popped on a stack, like JVM bytecode. i32.const 7; i32.const 3; i32.add leaves 10 on the stack.
  • Linear memory. A single contiguous byte array — initially up to 4GB. Every load and store is an offset into it. There are no pointers, no garbage collection, no concept of an "object."
  • Static types at the function-signature level. Originally just i32 / i64 / f32 / f64. Recent extensions add SIMD vectors and a handful of reference types.
  • Imports and exports declared explicitly. A module says "I import a function called console.log with signature (i32) -> void", and the host wires it up at instantiation time.
  • Sandboxed by construction. No syscalls, no filesystem, no clock, no anything — only what the host provides. The module can only touch its own linear memory.

Crucially: the WASM spec has no concept of objects, classes, garbage collection, threads, or a standard library. It's a thin layer over hardware. Everything higher-level is built on top by the source language's runtime — which the language ships inside the WASM module.

Act II ≣

WASM is not a JVM — same family, very different philosophies

Both are stack VMs with bytecode and JIT compilation. The similarity ends about there.

JVM WASM
Designed for Java (1995) Any compiled language (2015)
Type system Rich: objects, refs, classes, interfaces, generics Just i32/i64/f32/f64 originally; SIMD + ref types since
Memory Object heap with managed references Flat linear byte array — you manage offsets
Garbage collection Built into spec — mandatory None (until "WasmGC" recently — still optional)
Threads First-class, with synchronized, volatile, j.u.c Single-threaded by default; threads proposal adds shared memory + atomics
Standard library Massive — java.* shipped with the runtime None — host provides everything
Runtime size ~150MB JRE + small per-class files No runtime in spec; per-module ~tens of KB
Execution tiers Interpret → C1 → C2 (tiered JIT) Liftoff (baseline) → TurboFan (optimizing) in V8

The headline difference: JVM is opinionated, WASM is a substrate.

JVM bytecode reflects Java semantics — .class files, constant pools, monitor-enter/exit, virtual dispatch. Other JVM languages (Scala, Clojure, Kotlin) had to bend their semantics to fit Java's worldview. WASM is closer to LLVM IR. Each source language brings its own conventions on top, and the runtime knows nothing about them.

Concretely: when you compile Clojure to JVM bytecode, the JVM understands the methods, types, and references directly — because it is Clojure's runtime, by way of being Java's. When you compile Go to WASM, you get a binary that internally implements all of Go's memory model and garbage collector and goroutine scheduler using just i32 ops and linear memory. The WASM runtime has no idea what a goroutine is. It just sees a function executing with some bookkeeping.

Act III ⊜

How Go targets WASM — compile the runtime in, then your code

Go has supported GOOS=js GOARCH=wasm since Go 1.11 in 2018. More recently GOOS=wasip1 for non-browser WASI environments. Both are emitted directly by the Go compiler — no LLVM, no Emscripten. Go ships WASM as a first-class platform.

The catch is what gets put into that binary. Every Go WASM module includes the full Go runtime: garbage collector, goroutine scheduler, slice and map primitives, the syscall layer, the lot. That's the price of saying "Go runs here." The output looks roughly like this:

[your Go code] + [Go runtime — GC, scheduler, syscall/js, runtime primitives] → 5–15MB .wasm

The runtime knows how to allocate into Go's heap (a region of WASM linear memory it manages), how to run GC over that heap, how to schedule goroutines cooperatively on the single thread, and how to talk to the outside world via syscall/js. Once the module is loaded and the runtime initializes, main() starts and it looks essentially like Go is running — just slower, and with a different system layer beneath.

Go's single-threaded WASM is a deliberate choice. The WebAssembly Threads proposal exists, and SharedArrayBuffer + atomics make true parallel goroutines technically possible. The Go team has not implemented it. So in WASM, all goroutines cooperatively time-share the single thread — exactly as if you ran with GOMAXPROCS=1.

Act IV ⌭

The bridge — wasm_exec.js — the operating system Go expects to find

When the Go compiler emits a WASM module, it expects to find a host environment that provides certain imports. Things like runtime.wasmExit, runtime.wasmWrite, syscall/js.valueGet, syscall/js.valueSet, scheduler glue. Without these the module is dead — it has no way to do I/O, allocate from the browser's perspective, or yield to the event loop.

The Go toolchain ships a JavaScript file, wasm_exec.js, that provides all of these. It's essentially the operating system for Go-in-the-browser. Three jobs:

  • Imports the Go runtime expects. Every syscall Go would normally make to Linux/Darwin/Windows is rerouted to a JS function.
  • A Go-side "JS values" registry. When Go code does js.Global().Get("document"), the JS value gets stored in a JS-side map keyed by an integer ID. Go holds the ID. The bridge marshals between integers and references this way.
  • Scheduling glue. When Go calls time.Sleep or blocks on a channel, the runtime sets a JS setTimeout and yields back to the event loop. When the timer fires, JS pokes Go back into running.

wasm_exec.js isn't a part of the WASM spec — it's a Go-specific contract between the Go runtime and JavaScript. Other languages that target browser WASM bring their own equivalent.

Act V ⌬

Where our stack actually runs — two threads, one bundle, many layers

xsofy isn't a typical Go WASM app. It compiles a Clojure-dialect game to a bytecode interpreter (let-go) that itself was compiled to Go that was compiled to WASM that runs in a Web Worker that communicates with the main thread that hosts xterm.js. Five layers between your keypress and the cell that gets painted.

browser tab (main JS thread) ├─ wasm_exec.js — Go ↔ JS glue ├─ xterm.js — terminal emulator, canvas paint ├─ shell.html — D-pad, perf bar, _lgKey └─ Worker thread └─ WASM module ├─ Go runtime — GC, scheduler, syscall/js └─ let-go interpreter — Go code └─ xsofy bytecode — interpreted .lgb └─ game logic

A keystroke makes the journey twice — once in via SAB, once out via postMessage:

  1. Touch button or xterm.js calls _lgKey('h') on the main thread.
  2. Main thread writes a byte into the SharedArrayBuffer and calls Atomics.notify.
  3. The worker thread, parked in Atomics.wait, wakes up.
  4. Go's read-key reads the byte from SAB, returns into let-go.
  5. let-go's bytecode interpreter dispatches into the game's input handler.
  6. The game runs update-world, emits ANSI characters via term/write.
  7. Those bytes accumulate in a Go-side buffer.
  8. term/flush posts the buffer to the main thread via postMessage.
  9. The main thread feeds the bytes to xterm.js; xterm parses ANSI and repaints the canvas.

Critical detail explaining the architecture: Atomics.wait cannot run on the main thread — browsers refuse to let the main UI thread block synchronously. So Go's read-key has to live on a Web Worker. The worker can't touch the DOM. So xterm.js, which needs canvas access, has to live on the main thread. Result: the postMessage hop between them is unavoidable.

Act VI ⌗

Why we pay 10–15× — stacking taxes, not one big one

Pure Go-to-WASM is typically 2–3× slower than native Go. Our observed 10–15× tax comes from layering. Each one adds a multiplier:

  1. Single-threaded. Go's scheduler can't parallelize across cores; goroutines time-share one WASM thread. A multi-core CPU sits idle. GOMAXPROCS=1 in spirit.
  2. JIT vs AOT. V8's Liftoff/TurboFan tier is fast but not as good as Go's native AOT optimizer. No CPU-specific intrinsics. Bounds checks on every memory access. No PGO.
  3. let-go is an interpreter, not a compiler. Every Clojure op is a Go function call dispatched off bytecode. Native Go doesn't have this layer either. It's structural to running a dynamic language on a static VM on an abstract CPU on a JIT.
  4. GC pressure compounds. let-go allocates heavily — persistent maps, vectors, lazy seqs — and Go's GC running inside WASM has more overhead than native GC. Heap scanning has to bounds-check; allocations can't use OS huge pages.
  5. Boundary crossings cost microseconds each. Every postMessage and SAB notify is a few μs. Negligible for one event. For sustained input loops or rapid frame updates it adds up.
  6. No SIMD where it matters. Native Go can use AVX/SSE; WASM SIMD exists but neither the Go compiler nor let-go targets it. Color blending in render, bit-twiddling in the VM — all scalar.

Most of these we cannot fix without changing the WASM runtime itself. The Go team is working on better WASI support; V8 keeps improving its tiers. But for now, "10–15× native" is roughly the floor for our specific stack — and that's exactly what the in-bundle bench shows.

Where to go from here

Some threads worth pulling, if any of this sparked something:

  • WasmGC — the spec extension that adds garbage-collected references to WASM. Java has already shipped a JVM-in-WASM that uses it. Go has no plans yet; it'd be a major runtime rewrite.
  • WebAssembly Threads — adds shared linear memory and atomics. Go could theoretically use this for real parallel goroutines, but the runtime team has chosen not to so far.
  • WASI — WebAssembly System Interface. The "stdlib" analog for non-browser WASM. GOOS=wasip1 targets it.
  • Component Model — a higher-level interface description for WASM modules. Aims to make cross-language interop work without each language inventing its own bridge.
  • Our specific mystery — why a cache-invalidation gate that reduced native allocations by 10% made WASM measurably slower. See docs/project_notes/perf-audit-2026-05-18.md Phase 6 follow-up. Possibly a clue to something in let-go's WASM runtime we don't understand yet.
