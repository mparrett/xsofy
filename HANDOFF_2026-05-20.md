## What's Solved

### Input pipeline (i)

**Before:** Hold a direction into a wall → OS auto-repeat at ~30Hz, engine at ~20Hz, queue depth grows to 7+ slots → `i = 351ms` perceived input lag. New keypresses joined the back of the queue.

**After (Tier 1 = consumer-side lazy coalesce in `read-key`):** After consuming slot N, peek N+1 — if same bytes, advance past it. Loop. Held-wall: queue collapses on every read, depth never exceeds 1, `i = 0-1ms`. Distinct intents (move/attack/move) stay intact because legitimate human tap rate (5-10Hz) is slower than engine processing (~20Hz busy), so non-repeat sequences never queue past depth 1.

See `docs/input-pipeline-design.{md,html}` for the full design space (5 places intelligence could live, Tier 2 = queue cap 4, Tier 3 = JS producer dedupe). Tiers 2/3 unimplemented — held in reserve.

### Render spike (r)

**Before:** Every player move shifted the camera by 1 cell, triggering `render-dirty`'s full-window-repaint branch (`render-map` over ~1300 cells × ~0.14ms/cell on WASM = ~180ms spike on every move).

**After (dead-zone camera in `render/camera-for`):** Camera holds its last committed position until the player is within `camera-margin=8` cells of the visible window's edge, then shifts just enough to put the player at that margin. Most moves stay in the dead-zone → camera doesn't shift → FOV-delta render path → cheap. Floor changes still trigger a recenter (depth check on the stored camera atom). Subjectively the user reports "feels better, less big spikes."

### Display alignment

**Before:** Gauge lagged by one turn (by design — can't show this turn's number without rendering twice); bar showed current turn → mismatch under any input load. Then I added a 1-event JS-side lag to the bar, but the gauge's xterm-paint pipeline could fall further behind under rapid input, so they still drifted.

**After (turn labels on both):** Bar shows `@tN` prefix; gauge shows `tN` prefix. When they match, both are showing the same turn. When they drift, the lag is visible instead of misleading.

### Stale c bug

Cells counter was reset inside `render-full`/`render-dirty` only; mode-change turns (inventory, confirm dialogs) skip render entirely, so `c` displayed leftover values from the previous turn. Fixed by centralizing the reset in `main.lg` at the start of each `:game` iteration. Removed the now-redundant resets from render-full/render-dirty.

## Open Mysteries (worth chasing)

### Why did the `:lights` cache-invalidation fix regress WASM?

Commit `5d2b591` gated the cache invalidation in `step-fire` on actual terrain mutation. Native bench: -10.3% allocs, win. Live WASM phone: gauge climbed to 100-200ms+ on idle turns vs ~10-50ms with the original unconditional invalidation. **Reverted in `bfb0f87` without understanding the cause.**

Semantic difference: with the fix, idle turns preserve the `:lights` vector across turns instead of recomputing. The cached vector has stable content (~10-20 light-source maps for a typical floor). Render iterates `:lights` per visible tile via `light-at`. Why would WASM punish the preserved-vector path when it's *strictly less work*?

Working hypotheses (all unverified):
- Persistent vector identity tracking quirk in let-go's WASM runtime
- WASM GC keeps the cached vector pinned longer than native, increasing scan cost
- Render-side closure capture cost when the lights vector is the SAME identity across calls

Worth instrumenting: bench specifically isolates the engine. The regression was render-side. We need to drill into render paths to find why.

### Lingering baseline shift?

User reported earlier that even without my fire.lg fix, the bundle was "subjectively better but still hits 200ms+ spikes" relative to the ~12ms calm baseline they remembered from yesterday. Bundle xsofy code was identical to yesterday's working bundle at the time. The lg binary was freshly built today. So either the lg binary diff (ring buffer code) is somehow more expensive, or the user's "yesterday's 12ms" memory was from a different scenario.

Now that dead-zone camera ships, this might be moot — but worth a side-by-side WASM bench comparison if the question resurfaces.

## Key Decisions

### Why Tier 1 first, not Tier 2/3

`docs/input-pipeline-design.md` lays it out: consumer-side lazy coalesce in `read-key` is the cleanest semantics-wise. It collapses N identical adjacent slots to one return value, which is exactly what we want for OS auto-repeat into a wall. Distinct intents stay intact because deliberate human tap rates are *slower* than engine processing, so non-repeats never queue past depth 1. Queue cap and producer dedupe both have legitimate use cases but they're addressing scenarios we haven't observed failing. Ship the cheapest most-localized fix first; observe.

### Why a render-local atom for camera state

Considered storing camera on the world (`:camera-cx :camera-cy`) and threading it through `update-world`. Decided against because (a) camera is purely a render concern — the engine has no business knowing about it, and (b) the let-go runtime is single-threaded in both native and WASM modes, so an atom is fine. `render-full` and `render-dirty` call `commit-camera!` once at the end so siblings like `animate-vfx!` don't accidentally advance the camera between turns.

### Why label the gauge with `tN` instead of trying to align the bar perfectly

DOM `textContent` mutations paint faster than xterm-canvas character updates. The two displays will always drift slightly under rapid input — trying to compensate with heuristic JS-side delays is fragile. Explicit per-display turn labels make the lag legible instead of misleading.

### Why revert the `:lights` fix instead of pushing through

Project rule: "commit if delta > 10%." Native bench delta was +10.3% (good). WASM live testing delta was *negative* and significant. Without a clean explanation, shipping the change makes the user's actual environment worse — exactly what we're trying to avoid. Reverted and documented; will re-attack with better instrumentation.

The camera atom (`render/last-camera`) is not reset when entering inventory, confirm dialogs, etc. — only on floor change (depth check). This is intentional: the player's position hasn't changed, so the camera shouldn't move. But if a future code path teleports the player without changing depth (warp scrolls, recall), the camera will stay where it was. Add a recenter call if/when those features land.

### `c` is from the most-recent actual render
